## About

ones.

</Callout>

## Writing your own extensions

Beyond the built-in ones, you can teach the encoder and the decoder how to
handle your own types by implementing the `MessagePackExtension` interface.

Take a class that MessagePack knows nothing about:

```ts
class Point {
  readonly x: number;
  readonly y: number;

  constructor(x: number, y: number) {
    this.x = x;
    this.y = y;
  }
}
```

Encoding it without an extension would produce a plain map, and decoding it back
would return a plain object instead of a `Point`. An extension fixes that:

{/* prettier-ignore */}
```ts
import {
  type ExtensionEncoder,
  type MessagePackDecoder,
  type MessagePackExtension,
} from '@schema-pack/message-pack';

class PointExtension<
  TBuffer extends Uint8Array = Uint8Array,
> implements MessagePackExtension<Point, TBuffer> {
  readonly type = 10;
  readonly constructors = Point;

  encode(value: Point, encoder: ExtensionEncoder<TBuffer>): void {
    encoder
      .writeNumber(value.x)
      .writeNumber(value.y);
  }

  decode(decoder: MessagePackDecoder<TBuffer>, _size: number): Point {
    const x = decoder.nextValue<number>();
    const y = decoder.nextValue<number>();

    return new Point(x, y);
  }
}
```

Where:

- `TBuffer` is the buffer type used by the encoder and decoder. It defaults to
  `Uint8Array`, but you can use a custom type if you need to.
- `type` is the extension type id. It must be an integer between `0` and `127`,
  and unique among the extensions registered on the same encoder/decoder
  (`addExtension` throws otherwise). Negative types (`-1` to `-128`) are
  reserved by the [MessagePack extension types][MessagePack extension types]
  specification.
- `constructors` is the class or classes this extension handles (can be an
  array, like `readonly constructors = [Point]`). The encoder resolves the
  extension from the value's own constructor, so a subclass is not covered by
  its parent's entry: list it explicitly if you want it handled.
- `encode` writes the payload of the extension. Everything written here becomes
  the extension body, and the library takes care of the extension header (type
  and payload length) for you.
- `decode` reads that payload back, in the same order it was written.

`encode` receives an `ExtensionEncoder`, which exposes the same writing API as
the encoder itself (including `write`, which accepts any value the encoder
supports). That means an extension can nest arbitrary values (arrays, maps, or
values handled by other extensions), and `nextValue` reads them back one at a
time on the decoding side.

`decode` also receives the payload byte length as its second argument. The
example above doesn't need it, because it always reads exactly two values, but
it is what lets you decode variable-length payloads: keep reading while
`decoder.offset` is below the limit you computed from that size.

<Callout type='info'>
  Both `MessagePackExtension` and `ExtensionEncoder` accept a second generic
  parameter for the buffer type (`MessagePackExtension<Point, TBuffer>`). You
  only need it if you are working with a custom buffer type.
</Callout>

Then register the extension on both the encoder and the decoder:

```ts
import { Decoder, Encoder } from '@schema-pack/message-pack';

const pointExtension = new PointExtension();

const encoder = new Encoder().addExtension(pointExtension);
const decoder = new Decoder().addExtension(pointExtension);

const buffer = encoder.write(new Point(1, 2)).flush();

decoder.decode(buffer); // Point { x: 1, y: 2 }
```

Registering it only on the encoder produces a buffer nobody can read back, and
registering it only on the decoder leaves the value encoded as a plain map.

### Extensions only handle objects

The encoder looks up an extension from the constructor of the value being
encoded, and only object values have one it can use. Primitives (`number`,
`string`, `boolean`, `bigint`, `symbol`) never go through that lookup, so an
extension can't be used to change how they are encoded.

In practice, an extension handles values created with `new`: class instances,
including subclasses, as long as each constructor is listed in `constructors`.

<Callout type='info'>
  The [BigInt](./bigint) extension is the exception that proves the rule: it
  does handle a primitive, but only because it is implemented inside the encoder
  and the decoder themselves, not through the extension interface described
  here.
</Callout>
